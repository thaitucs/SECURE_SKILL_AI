# Contact anti-spam: email addresses, phone numbers, forms, OTP

**Why it matters:** spam bots do not look at the screen - they download the HTML/JS and
search for `something@domain.tld`, `mailto:`, `tel:` and digit patterns. Any address or
number in page source, bundles, JSON-LD or API responses is harvested within days and then
receives spam, phishing and robocalls. Unprotected forms are abused to send spam (to you,
or through you to others), and SMS/OTP endpoints are abused for "SMS pumping" fraud that
costs real money.

Nothing here is applied without the user's approval (`SPAM-*` items).

---

## 1. Decision guide

| Situation | Recommended combination |
|-----------|-------------------------|
| Static site, email shown only so visitors can contact you | Contact form via serverless function **+** honeypot + time-trap + rate limit (+ CAPTCHA if spam continues). Remove visible email, or keep a JS click-to-reveal fallback. |
| Business site that must show email (legal/imprint, B2B) | JS-assembled click-to-reveal link + role/alias address + strong mailbox filtering. |
| Phone shown for customers to call | Click-to-reveal / tap-to-call generated by JS, business or virtual number, callback-request form as an alternative. |
| Web app with user profiles | Never expose other users' email/phone in API responses or HTML; mask (`j***@gmail.com`, `090****123`); show full data only to the owner/admin. |
| Signup / login / reset / newsletter forms | Rate limit + CAPTCHA (invisible) + email verification / double opt-in + disposable-email check (optional). |
| SMS/OTP sending | Rate limit per phone/IP/device, CAPTCHA before sending, geo allow-list, provider fraud guard, exponential back-off. |

## 2. Techniques for showing an email address

Ranked from strongest to weakest. Combine 2-3.

| # | Technique | Protection | UX / accessibility | Notes |
|---|-----------|-----------|--------------------|-------|
| 1 | **Don't show it - contact form** | Very high | Good if the form is accessible | Destination address stays on the server |
| 2 | **Click-to-reveal button** (address fetched from backend or assembled in JS on click) | High | Good with a labelled `<button>` | Bots rarely click |
| 3 | **JS assembly on load** (parts in `data-` attributes, joined at runtime) | Medium-high | Good; needs JS | Headless bots can run JS |
| 4 | Encoded string (base64 / ROT13 / reversed) decoded by JS | Medium | Good | Same as above |
| 5 | CSS tricks (`direction: rtl` reversed text, hidden spans) | Medium | Poor - copy/paste and screen readers break | Avoid for main contact |
| 6 | HTML entities (`&#106;&#111;...`) | Low | Good | Most harvesters decode entities |
| 7 | "name [at] domain [dot] com" | Low | Poor | Annoying, easily parsed |
| 8 | Image of the email | Medium | **Bad** (not accessible, not clickable) | Do not recommend |

**Also**
- Use a **role or alias address** (`contact@`, `support@`, forwarding alias) instead of a
  personal one. If it gets spammed you can rotate it without changing your real mailbox.
- Use **plus-addressing** or separate aliases per channel to see where spam comes from.
- Remove the address from places that do not need it: HTML comments, `meta` tags,
  `humans.txt`, JS config, JSON-LD (trade-off: local SEO - user decides), PDFs on the site.

### Click-to-reveal example (no dependency)

```html
<button type="button" class="reveal-contact" data-u="hello" data-d="example.com">
  Show email address
</button>
<script>
document.querySelectorAll('.reveal-contact').forEach(function (btn) {
  btn.addEventListener('click', function () {
    var addr = btn.dataset.u + '@' + btn.dataset.d;
    var a = document.createElement('a');
    a.href = 'mailto:' + addr;
    a.textContent = addr;
    btn.replaceWith(a);
    a.focus();
  });
});
</script>
<noscript>Please use the contact form.</noscript>
```

Stronger variant: the button calls `GET /api/contact-email` (rate-limited, optionally behind
CAPTCHA) and the address never appears in the static files.

## 3. Phone numbers

- Prefer a **business, virtual or call-forwarding number**, never a personal mobile.
- **Tap-to-reveal**: show `090x xxx x23 - Show number`; build the `tel:` link in JS on click
  (same pattern as email). Same for WhatsApp / Zalo / Telegram / Viber links.
- Offer a **callback request form** ("Leave your number, we call you") protected like any
  form.
- Do not put the number in plain text in `meta`, JSON-LD or image `alt` if harvesting is the
  main concern (trade-off with local SEO / Google Business - user decides).
- Use carrier/app spam filtering and call screening on the receiving side (`[YOU]`).

## 4. Form protection (contact, newsletter, signup, comments, reset)

Layered - all enforced **on the server**:

1. **Honeypot field**: an extra input hidden with CSS (not `type="hidden"`), named like a
   real field (`website`, `company_url`), `tabindex="-1"`, `autocomplete="off"`,
   `aria-hidden="true"`. If filled → silently accept and drop.
2. **Time-trap**: server-signed timestamp issued when the form renders; reject if
   submitted in < 3 s or after many hours.
3. **Rate limit**: per IP and per target (email/phone), e.g. 5 per 10 min per IP for contact
   forms, 3 per hour per phone for OTP.
4. **CAPTCHA** (invisible/managed first): Cloudflare Turnstile, hCaptcha, Google reCAPTCHA
   v3/Enterprise. **Verify the token server-side** with the secret key. Site key is public,
   secret key is backend-only.
5. **Validation**: length limits, required fields, valid email syntax, reject or flag
   messages with many URLs, strip HTML, block CR/LF in any value used in email headers
   (header injection).
6. **Never** take the recipient address from the form (classic open relay). Recipient is
   fixed on the server.
7. **No echo auto-replies** to the submitter containing their message - spammers use this to
   send spam through you. A fixed "We received your message" is OK, ideally only after
   verification.
8. **CSRF token** if the form uses cookie-based sessions.
9. **Double opt-in** for newsletters/marketing lists.
10. Optional: disposable-email domain list, sender reputation, keyword filters,
    moderation queue for public comments.

### Honeypot + time-trap (server side, Node/Express example)

```js
// routes/contact.js  (backend)
const MIN_MS = 3000;
router.post('/contact', rateLimit({ windowMs: 10 * 60e3, max: 5 }), async (req, res) => {
  const { name, email, message, website, ts, sig } = req.body;
  if (website) return res.status(200).json({ ok: true });            // honeypot: drop silently
  if (!verifySignedTimestamp(ts, sig) || Date.now() - Number(ts) < MIN_MS)
    return res.status(400).json({ error: 'Please try again.' });     // time-trap
  if (!(await verifyTurnstile(req.body['cf-turnstile-response'], req.ip)))
    return res.status(400).json({ error: 'Verification failed.' });
  if (/[\r\n]/.test(name + email)) return res.status(400).end();      // header injection
  await mailer.send({ to: process.env.CONTACT_TO, replyTo: email,
                      subject: 'Website contact', text: String(message).slice(0, 5000) });
  res.json({ ok: true });
});
```

### Turnstile server verification

```js
async function verifyTurnstile(token, ip) {
  if (!token) return false;
  const r = await fetch('https://challenges.cloudflare.com/turnstile/v0/siteverify', {
    method: 'POST',
    body: new URLSearchParams({ secret: process.env.TURNSTILE_SECRET_KEY, response: token, remoteip: ip }),
  });
  return (await r.json()).success === true;
}
```

PHP equivalent: check `$_POST['website']` is empty, compare signed `ts`, call siteverify with
`curl`/`file_get_contents` + `stream_context_create`, use PHPMailer with a fixed recipient.

### Static site without a server

Use the host's form feature (Netlify Forms with honeypot, Formspree, Getform, Basin...) or a
small serverless function (Vercel/Netlify/Cloudflare Workers/Firebase Functions). If a
third-party form service is used, the destination address is configured in their dashboard,
not in the HTML.

## 5. Signup, login and OTP / SMS abuse

- **Login/signup/reset**: rate limit per IP and per account, progressive delays, CAPTCHA
  after N failures, generic error messages ("If an account exists, we sent an email").
- **SMS pumping / toll fraud**: attackers trigger OTP SMS to premium numbers. Defences:
  CAPTCHA before sending, rate limit per phone + IP + device, allow-list countries you serve,
  block number ranges, max resend count, exponential back-off, provider fraud protection
  (e.g. Twilio Verify Fraud Guard), alerts on SMS spend (`[YOU]`).
- **Email verification** before the account can send messages, invite others, or post.
- **Enumeration**: same response and timing for existing and non-existing accounts.

---

## 6. Data leaks of contact info in apps

- API endpoints returning full user objects (`/api/users`, `/api/posts?include=author`)
  must not include other users' email/phone. Use explicit response DTOs/serializers.
- Mask in lists, full value only to the owner/admin; log access to contact data for admins.
- Avoid exposing contact info in public profile pages unless the user opted in.

These are **privacy** findings (category `auth` if access control is missing, `abuse` for
harvesting risk).

---

## 7. Mail domain protection (`[YOU]` items)

- **SPF** record listing your senders, **DKIM** signing, **DMARC** (`p=quarantine` or
  `p=reject` once reports are clean) - stops others from spoofing your domain and improves
  deliverability of your form emails.
- Send form emails **from** your domain via an authenticated provider (SMTP/API), with
  `Reply-To` set to the visitor - never `From: visitor@...`.
- Enable your mail provider's spam filtering; create rules for the public alias.

---

## 8. Severity defaults

| Finding | Severity | Category |
|---------|----------|----------|
| Form lets the visitor choose the recipient / header injection possible | High | abuse |
| OTP/SMS endpoint with no rate limit or CAPTCHA | High | abuse |
| Other users' emails/phones returned by API | High | auth |
| Contact/signup form with no server-side spam protection | Medium | abuse |
| Login with no rate limit / lockout | Medium | abuse |
| Email/phone in plain text in page source | Low | abuse |
| Personal (not role) address or personal mobile shown | Info (advice) | abuse |
